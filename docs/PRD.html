1. Product vision

The goal is to build a polished, futuristic, rhythm-driven block puzzle game that captures the hypnotic satisfaction of Lumines, combines it with the familiar shapes of Tetris, and runs beautifully in a browser on desktop and mobile.

The core experience is simple: play endlessly, survive as long as possible, beat your personal best, and share your score with friends.

The game should feel like a premium arcade experience rather than a conventional web game. Saturated colors, crisp geometric artwork, tactile block placement, 2.5D depth, rhythmic animations, and a responsive interface should feel equally natural on a phone held vertically, a phone held horizontally, or a desktop monitor.

Product principles

  1. Instantly understandable. Familiar seven-piece tetromino shapes, intuitive controls, and a clear objective.
  2. Endlessly replayable. No final level or campaign; the goal is to survive and improve.
  3. Rhythmic and hypnotic. A sweeping timeline clears completed color blocks.
  4. Beautiful without clutter. Saturated colors against a deep, solid background. No gradients.
  5. Mobile-first. Portrait and landscape are first-class layouts with distinct controls.
  6. Private and offline-friendly. Scores, settings, and records remain on the device.
  7. Socially shareable. Send scores through native sharing, SMS, or WhatsApp with a link back to the game.

Product goals

  • Playable within seconds of opening the website.
  • Every run challenges players to beat their previous record.
  • Records survive reloads and PWA launches.
  • Installable PWA behavior on supported browsers.
  • Consistent gameplay across screen sizes and orientations.
  • Original visual identity inspired by the genre, without copying proprietary assets.

Central gameplay concept

The game combines falling-block puzzle mechanics—seven recognizable tetromino shapes, stacking, rotation, collision, and game-over—with a rhythm-puzzle mechanic: a timeline sweeps across the board and clears qualifying groups of matching color cells when it passes them.

Important distinction: The pieces retain exact tetromino geometry, but this is not standard Tetris. The signature mechanic is color-based, beat-driven clearing.

The game should not require musical knowledge, precise timing, or sound to be playable. Audio and visual rhythm are complementary.

3. Core gameplay specification

3.1 The board

The playfield is a rectangular grid of 10 columns and 16 rows, with a hidden spawn area above the visible grid if needed. Each cell is empty or occupied by a color identity. Rendering metadata for depth, highlights, borders, and effects remains separate from logical state.

The logical board remains independent of screen size. The renderer scales the same board to available space on every device. Use a solid dark background, subtle cell separators, and a clean outer frame. Occupied blocks look like physical arcade tiles with shallow extruded sides and crisp edges.

3.2 The seven tetrominoes

I piece
J piece
L piece
O piece
S piece
T piece
Z piece

Each piece consists of exactly four orthogonally connected cells. Geometry stays fixed while color schemes can change. Do not invent new shapes, use five-cell pentominoes, or generate a predetermined pattern of piece types.

3.3 Completely random piece generation

The user explicitly requires that the order of pieces be completely random. Implement independent uniform random selection from the seven piece types:

P(each piece) = 1/7
Do not use a seven-bag system, shuffled deck, guaranteed sequence, or rules that force all seven pieces to appear before repeats. Repeated identical pieces in a row are expected.

Use a seeded pseudorandom generator for reproducible development tests and a randomly seeded generator for ordinary gameplay. Randomness must be independent of player performance.

3.4 Color assignment

  • Each piece has two color identities, with two cells per color.
  • The arrangement varies between pieces.
  • The O piece follows the same two-and-two rule.
  • Color assignment is randomized independently of piece type.
  • Palette colors remain stable during a run.
  • Theme changes between runs or milestones must not silently recolor existing cells in ways that change matching behavior.

4. Signature mechanic: the sweep line

A bright, sharply defined vertical line continuously moves from the left side of the board to the right. At the right edge it wraps to the left and begins another sweep. Its movement is independent of falling-piece gravity.

4.1 Matching and clearing rules

A completed match is a solid, monochromatic 2×2 square or a larger rectangular group composed entirely of 2×2 squares. A match becomes eligible when four same-colored occupied cells form a 2×2 square, the square is stable, and the sweep reaches its clearing zone.

The board uses connected components of same-colored cells. Only complete 2×2 squares count; arbitrary clusters without a full 2×2 square do not clear. If a component contains multiple complete 2×2 squares, count the maximum number of non-overlapping 2×2 squares that fit inside the component. Clear the component at the sweep event and award points based on the number of squares cleared.

4.2 Clearing resolution

  1. The timeline reaches a cell column.
  2. Eligible matching components intersecting that column are identified.
  3. Groups are evaluated against a stable snapshot of the board.
  4. Qualifying cells are marked for clearing.
  5. A short visual effect plays.
  6. Cleared cells are removed.
  7. Gravity resolves floating cells or groups.
  8. The board is recalculated and normal play continues.

A clearing event must not award duplicate points because the line overlaps several cells in the same match. Simulation order must be deterministic; animation timing cannot change the logical result.

4.3 Timeline speed and difficulty

Time survivedTimeline speedPurpose
0–30 seconds0.45 columns/secLearn the mechanic
30–90 seconds0.65 columns/secEstablish rhythm
90–180 seconds0.85 columns/secIncrease pressure
3–5 minutes1.05 columns/secChallenge experienced players
5+ minutes1.25+ columns/secEndless survival pressure

These are initial tuning values. Use a continuous ramp rather than abrupt jumps. Falling-piece gravity should also increase gradually, but never so far that ordinary touchscreen movement and rotation become impossible.

4.4 Scoring

  • Each cleared 2×2 square: 100 points.
  • Additional adjacent squares cleared in the same event: +25 points per square after the first.
  • Combo bonus: multiplier based on successive successful sweep events.
  • Survival score: 1 point per second survived.
  • Hard drop: no direct score bonus.

Keep values configurable for playtesting. Survival points must not make ignoring the matching mechanic optimal.

4.5 Game over

The game ends when a newly spawned piece cannot fit at its spawn location, or when the locked stack exceeds the valid board boundary. Freeze gameplay, resolve pending score updates, save final results, update the personal best if appropriate, show a result overlay, and offer immediate restart and share actions. No lives, paid revivals, or artificial level-ending screens are required.

5. Visual direction and art bible

The game should feel like a premium electronic arcade cabinet reimagined as a modern, touch-first web experience.

Themes are cosmetic and must not affect gameplay or scoring. Color identity should not rely on hue alone; offer patterns or symbols as an accessibility option.

5.1 Core visual rules

  • Solid, nearly black navy background.
  • Saturated cyan, electric blue, magenta, coral, acid yellow, and mint green.
  • Physical-looking tiles with shallow extruded sides.
  • Crisp edges, consistent bevel geometry, thin borders, and precise alignment.
  • Subtle shadows for separation, not atmospheric haze.
  • Animation communicates gameplay events rather than decorating every interaction.
  • Flat, opaque colors only; no gradients anywhere.
Explicit no-gradient policy
No gradients in backgrounds, tiles, buttons, borders, text, modals, logos, loading indicators, score displays, or particles. A block may have a bright cyan top face, a darker solid cyan side, and a thin highlight. Depth comes from geometry and contrast, not gradients.

5.2 2.5D tile construction

Render each block from discrete shapes: a saturated top face, darker solid side faces, and a thin bevel highlight. Keep one consistent extrusion direction. Extrusion must not change logical tile dimensions or collision boundaries. Avoid excessive glow; any restrained glow should be optional and disableable.

5.3 Typography and iconography

  • Modern geometric sans-serif for interface text.
  • Monospaced or tabular numerals for score and time.
  • Compact, bold headings; high-contrast score; short supporting labels.
  • Consistent line weight and simple geometric icons.
  • No decorative typefaces that compromise small-screen readability.

6. Responsive UI and layout system

Responsive behavior is a core requirement, not a final styling pass. Use CSS Grid and Flexbox for the interface and a canvas-based high-performance renderer for the board. Use ResizeObserver and device-pixel-ratio-aware canvas sizing.

6.1 Layout modes

Mobile portrait — priority

  • Compact logo, best score, settings in header.
  • Score and survival time above board.
  • Board centered horizontally and scaled to available height.
  • Controls anchored at bottom.
  • No horizontal scrolling.
  • Respect browser chrome and safe areas.

Mobile landscape — priority

  • Compact score panel to one side.
  • Board centered in remaining space.
  • Controls beside or below board depending on height.
  • Hide nonessential labels and decoration.
  • Pause and drop controls stay reachable.
  • Orientation change must not restart the run.

Tablet

  • Flexible board and side panels.
  • Comfortable touch targets.
  • HUD scales without stretching the playfield.

Desktop

  • Spacious application shell.
  • Board centered at comfortable size.
  • Score, survival, best score, optional next-piece preview.
  • Keyboard controls primary.
  • Touch controls hidden unless touch is detected or enabled.

6.3 Board sizing

Keep the logical board at 10 × 16 while scaling the displayed cell size. Let Wa be available width, Ha available height, and C cell size:

C = min(Wa / 10, Ha / 16)
Board width  = 10 × C
Board height = 16 × C

Keep extrusion and frame padding outside logical cell dimensions so decorative depth cannot clip at board boundaries.

6.4 Safe areas and browser chrome

Support viewport-fit=cover, env(safe-area-inset-top), env(safe-area-inset-bottom), left/right safe areas, dynamic viewport units such as dvh, and fallbacks for browsers without dynamic viewport units. Account for toolbars expanding/collapsing, notches, home indicators, and installed-PWA display mode.

6.5 Orientation changes

Changing orientation must not restart the game, reset score or timeline, reorder/regenerate the current piece, alter logical board dimensions, trigger unintended inputs, or duplicate events. The renderer may briefly suspend drawing during resize, but simulation state must remain coherent.

6.6 Touch interaction and accessibility

Touch targets should ideally be at least 44 × 44 CSS pixels, with comfortable spacing. Held controls must stop on release, cancellation, interruption, or focus loss. Prevent unintended page scrolling only within the game surface; do not globally disable browser zoom or accessibility gestures. Avoid registering one gesture as both a swipe and a button press.

8. Score sharing and social distribution

Every completed run produces a concise, copyable message with score, survival time, and canonical game URL.

Example share message
“I scored 8,640 in BEAT//BLOCK and survived for 2:18. Can you beat me?

Play here: https://example.com”

Illustrative values. Production code inserts the real score, duration, and deployed URL.

8.1 Sharing channels

  • Native device sharing.
  • SMS/text message.
  • WhatsApp.
  • Copy link.
  • Copy score message.

Use the Web Share API when supported. Available targets vary by browser and device, so provide fallback buttons.

  • SMS: open the platform SMS composer with a URL-encoded message using an sms: link.
  • WhatsApp: open a WhatsApp share URL with URL-encoded text.
  • Copy: copy the full message to the clipboard.
  • Native share: pass title, message, and canonical URL to the system share sheet.

8.2 Share behavior

  1. Build the message from the completed run.
  2. Use the canonical production URL.
  3. Try native sharing when available.
  4. If unavailable or it fails for a reason other than user cancellation, show explicit channel buttons.
  5. Keep the game-over screen visible behind the share interface.
  6. Do not reset the game when sharing is cancelled.
  7. Do not claim a message was sent merely because a share sheet opened.

WhatsApp can use the https://wa.me/?text= pattern with encoded text. SMS link syntax varies across platforms, so test platform-specific formatting.

8.3 The shared link

  • Opens the playable game, not an external marketing page.
  • Works when pasted into a browser.
  • Requires no account or server session.
  • Uses HTTPS in production.
  • Includes page title, description, and social preview metadata.
  • Continues to work in browser and installed-PWA contexts.

The shared score is a claim in the message, not a verified global leaderboard entry. The local-only product must not imply scores are authenticated or other players' records are queryable. A future online leaderboard requires a separate server-backed feature and privacy design.

9.2 Storage strategy

Use IndexedDB as primary storage for versioned records and settings. localStorage may hold simple noncritical preferences if desired.

interface GameProfile {
  schemaVersion: number;
  personalBestScore: number;

The schema may evolve but must include migration. Invalid or outdated records must not crash the game.

9.3 Persistence behavior

  • Load records and settings before showing the fully interactive home screen.
  • Use safe defaults if no record exists.
  • Save high-score updates immediately.
  • Avoid storage writes every animation frame.
  • Save aggregate statistics at sensible intervals and on run completion.
  • Handle storage failure without breaking gameplay.
  • Keep gameplay functional if persistence is unavailable.
  • Offer a reset-data action with confirmation.

9.4 PWA installation and offline mode

Include manifest.webmanifest, app name and short name, 192×192 and 512×512 icons, standalone display settings, theme and solid background colors, start URL, HTTPS deployment, and a service worker.

After essential assets are cached, offline users can launch the app, play a full run, save scores locally, change settings, and view records. Sharing requires connectivity to open a destination or send a message, though share text can be prepared offline.

Use versioned caches and controlled updates. Updating must not erase records or interrupt an active game without warning.

10.3 Simulation loop

Use a fixed-timestep update loop with a separate rendering loop. Calculate elapsed time, add it to an accumulator, run fixed simulation steps while enough time remains, then render current state with optional interpolation. Limit excessive catch-up steps after tab suspension. Start at 1/60 second and make it adjustable.

10.4 Core game state

State machine: READY, PLAYING, PAUSED, GAME_OVER.

A run contains board occupancy, current falling piece, optional next-piece preview, gravity accumulator, timeline position and direction, score, survival duration, difficulty parameters, combo state, active palette, random generator state, and game status. Rendering must never consume random pieces; the piece generator produces and stores game state.

10.5 Board representation

type ColorId = 0 | 1 | 2 | 3 | 4 | 5 | 6;

interface Cell {
  occupied: boolean;
  color: ColorId | null;
}

type Board = Cell[][];

For performance, a compact integer representation may be preferable: zero means empty and positive values mean occupied colors. Keep rendering metadata separate from logical board state.

10.6 Piece representation

type PieceType = "I" | "J" | "L" | "O" | "S" | "T" | "Z";

interface FallingPiece {
  type: PieceType;
  rotation: 0 | 1 | 2 | 3;
  x: number;
  y: number;
  cellColors: ColorId[];
}

Each type has canonical cell coordinates. Rotation transforms coordinates around a defined pivot, with collision validation and wall kicks. The O piece remains geometrically unchanged when rotated.

10.7 Random generation

const TYPES = ["I", "J", "L", "O", "S", "T", "Z"] as const;

function nextPieceType(rng: () => number) {
  return TYPES[Math.floor(rng() * TYPES.length)];
}

Ensure the random function returns a value in [0, 1). Inject the generator into the engine for deterministic tests. In production, avoid allocating the array on every call.

10.8 Separation of concerns

  • The engine does not know about React components, DOM elements, or CSS breakpoints.
  • The renderer does not decide collisions, match clearing, or score.
  • The UI subscribes to selected state changes instead of rerendering the entire application every simulation tick.
  • The storage layer does not directly modify the active board.

11. Input architecture and mobile performance

11.1 Unified input system

Convert keyboard, touch, pointer, and optional gamepad input into game commands.

type GameCommand =
  | { type: "MOVE_LEFT"; pressed: boolean }
  | { type: "MOVE_RIGHT"; pressed: boolean }
  | { type: "SOFT_DROP"; pressed: boolean }
  | { type: "ROTATE_CW" }
  | { type: "ROTATE_CCW" }
  | { type: "HARD_DROP" }
  | { type: "PAUSE" };
  • No duplicated keyboard or pointer events.
  • Held controls stop on release, cancellation, blur, or pause.
  • Rotation and hard drop trigger once per activation.
  • Horizontal repeat uses controlled delay/rate, not uncontrolled browser key-repeat.
  • Touch controls never depend on hover.
  • All controls work in portrait and landscape.

11.2 Performance requirements

Target 60 FPS on supported mobile devices while remaining playable at lower frame rates. Avoid large allocations or React elements each frame. Cache static geometry where practical. Scale canvas backing resolution by device pixel ratio with a configurable cap. Avoid unnecessary canvas resizing and network requests. Suspend or limit catch-up when hidden, and resume safely on visibility changes.

Initial performance budget: complete update and rendering work within 12 ms per frame on the reference mobile device, leaving time for browser overhead.

11.3 Browser requirements

  • Chrome on Android.
  • Samsung Internet.
  • Safari on iOS.
  • Chrome and Edge on desktop.
  • Safari on macOS.

Test browser-tab and installed-PWA modes where supported. Handle blocked audio before user interaction, changing browser toolbar height, and orientation changes.

12. Audio and haptics

Audio reinforces rhythm but is never required for gameplay.

  • Movement: subtle tick.
  • Rotation: short tonal click.
  • Lock: low, satisfying impact.
  • Match: bright electronic accent.
  • Combo: layered ascending tone.
  • Game over: brief descending sequence.

Use original or properly licensed sounds; do not copy music or sound effects from Lumines or Tetris. The first release may use a looping electronic soundtrack or an original procedural rhythmic layer. Timeline speed and animation must not depend on the audio clock. Music begins after a user gesture where required.

Where vibration is supported, offer short optional pulses for hard drop, successful clear, and game over. Respect user preferences and browser limitations.

13. Settings and accessibility

Settings: sound effects, music, haptics, reduced motion, color theme, control layout, left-handed layout, high-contrast mode, and data reset.

  • Keyboard-operable menus and visible focus indicators.
  • Accessible labels for icon-only buttons.
  • Sufficient contrast for text and controls.
  • Non-color indicators for matching identities when requested.
  • No harmful flashing patterns.
  • Reduced-motion support and no forced audio.
  • Button alternatives for gestures.

The active board may use canvas, but the surrounding interface must use semantic HTML and clear accessible labels.

17. Key product risks and mitigations

Matching mechanic is confusing

Teach the 2×2 color-matching rule through a short interactive tutorial and first-run demonstration.

Board is unreadable on small phones

Prioritize logical cell size, reduce decorative depth, and simplify HUD before shrinking interactive controls.

Random sequences feel unfair

Keep genuinely independent randomness; tune gravity, board dimensions, and clearing rules through playtesting. Never secretly manipulate piece probabilities based on player state.

Animation interferes with gameplay

Separate simulation updates from effects; keep the board state authoritative.

Browser clears local storage

Use IndexedDB, handle missing data gracefully, and explain that local records can be lost if site data is cleared.

Sharing differs by device

Use native sharing when available and explicit channel links plus copy controls as fallbacks. Test message composition on Android and iOS.

18. Final implementation instructions and definition of done

  1. Randomness: Each tetromino type is selected independently and uniformly. Never use a seven-bag generator or fixed repeating sequence.
  2. Shape fidelity: Only the seven standard four-cell tetrominoes are permitted.
  3. Gameplay identity: Retain rhythm-driven sweep line and color-based square clearing.
  4. Responsive design: Mobile portrait and landscape are equally important primary experiences.
  5. Logical consistency: Board dimensions and game state remain stable across breakpoints.
  6. Visual identity: Saturated colors, discrete 2.5D geometry, solid fills, and no gradients.
  7. Persistence: Scores, records, and preferences are local. No account or server is required for core gameplay.
  8. Sharing: Every generated message includes actual score, survival time, and canonical URL.
  9. Offline support: Core game works offline after required resources have been cached.
  10. Quality: Automated tests validate gameplay separately from visual rendering.
Definition of done
A new player can open the website, understand the objective, start playing immediately, rotate and move pieces comfortably on a phone, survive multiple timeline sweeps, see the final score, save a personal best locally, and challenge a friend through a working share link.

The experience should feel like a compact, premium arcade game that happens to run on the web—not a desktop game squeezed into a phone screen.

Recommended implementation order: gameplay correctness → responsive controls → visual polish → local persistence and PWA → sharing → cross-device QA.
